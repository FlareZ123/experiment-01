One concrete reason the host-side bounds check is worthwhile: the current prompt-projection test fixture's `ChoosePokemonPrompt.validate()` only checks `result.length > 0`; it does **not** enforce `options.min/max`. The normal Docker session path is protected by `protocol.validateDecision()`, but `dispatchPromptChoice()` can be called directly and its native validation is not a universal cardinality guarantee. Reusing `protocol.multiSelectBounds(projection.promptProjection)` at the dispatch boundary would make the host mapping self-contained and keep the same bounds authoritative on both sides.
