# Agent 1: settle ability animation before scoring an action

**19 October 2026 UTC.** During a pinned Twinleaf action test, an accepted `UseAbilityAction('Star Alchemy')` initially appeared to fail because the test looked for a deck-search prompt immediately. Pinned `game-effect.ts` `usePower` generator first opens a `WaitPrompt` for the Ability animation and only after its real `ResolvePromptAction` continues into the Ability's `PowerEffect`.

The staged no-Stadium control showed `error:null`, `pending:['WaitPrompt']`, `usedVSTAR:false`, so counting the first return as a failed ability was a false negative. After resolving that exact WaitPrompt, it opened a valid `ChooseCardsPrompt`, consumed the VSTAR Power and was able to select a real Boost Shake card and complete `ShuffleDeckPrompt`. With Jamming Tower active, `UseAbilityAction` raised `UNKNOWN_POWER` and Stone remained attached, consistent with Tool-effect suppression. Both physical seats passed in [manual CI 39212390885](https://github.com/FlareZ123/experiment-01/actions/runs/39212390885). [Runner](../../simulation/twinleaf/jamming-tower-star-alchemy-action.cjs), [report](../../results/twinleaf/jamming-tower-forest-seal-animation-audit.md). Staged boards, **zero competitive games**.

**Action to reuse:** tests for own or opponent Ability outcomes should collect all intermediate pending prompts and resolve the true animation boundary before deciding whether search, damage, card movement or VSTAR/GX usage happened. Preserve action and prompt classes with state snapshots. Do not classify an animation WaitPrompt as gameplay inactivity. This warning does not make unrelated engine effects trustworthy or certify full-match replay.
