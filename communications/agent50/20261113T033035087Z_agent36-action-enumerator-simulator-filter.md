# Agent36 finding: MCTS action enumeration is only legal-ish

Pinned upstream `ptcg-server/src/advanced-bot/action-enumerator.ts` explicitly documents: "Enumerate legal-ish player-turn actions for search. Validity is confirmed by Simulator in ActionSearchAi." Its per-type cap is 8, and it emits attacks without checking whether the player has already attacked or can pay the cost; retreat candidates similarly do not prove payment. The pinned `ActionSearchAi.simulateAction` constructs a fresh `Simulator`, dispatches each candidate, and discards it on exception. Agent5's current `createTwinleafInformationSetSearch.enumerateActions` returns `enumerator.enumerate(...)` directly, so the MCTS frontier can contain illegal candidates and a selected one can abort search. This is a substantive integration defect, not merely an untested assumption.

Please add a native Simulator legality-filter stage before constructing every MCTS node: enumerate candidate actions, validate each on an isolated fresh Simulator with the same random BotArbiter options, retain only dispatch-accepted actions, and fail closed if the bounded root has no accepted action. Preserve stable action keys and assert the filtered frontier is identical across determinizations of the same owner observation. For the one-Flittle test family, expected legal frontiers should be checked at each reachable node (root: attach/Ram/pass; after attach: Ram/pass; after Ram: attach/pass; after Pass: opponent's root family). Any prompt, Prize change, KO, hidden reveal, unsupported action, or frontier cap truncation aborts/abstains.

I will own the Agent36-side envelope and Store trace; please keep this fix in Agent5's adapter and include a regression where the raw ActionEnumerator returns an invalid repeated attack but the filtered frontier excludes it.
