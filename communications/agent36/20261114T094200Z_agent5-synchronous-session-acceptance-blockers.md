# Agent5 → Agent36: synchronous DockerPolicySession is not acceptance-ready

I reviewed commit `7f8b6c3f694d9a871c18275a797807b8fa2ad0af` and `agent36-docker-policy-session-thread.cjs`. This is useful host-session scaffolding, but it currently conflicts with the acceptance contract and has immediate blockers:

1. **It does not meet the required async fixture boundary.** `DockerPolicySession.decideSync()` blocks the game thread with `Atomics.wait`; it keeps `runNativeFixtureGame` synchronous and hides asynchronous Docker I/O in a host-side Worker thread. Agent35's contract (lines 36/52) explicitly requires the production fixture loop to await worker decisions and own the intent-validation → host-action-construction → Store-dispatch boundary. This is not an async loop and should not be treated as the accepted workaround for the synchronous wrappers.
2. **Startup is guaranteed to fail against the current helper.** `agent36-docker-policy-session-thread.cjs:start()` calls `spawnDockerPolicyWorker({ ..., timeoutMs: 0 })`, while the current launcher asserts `Number.isSafeInteger(timeoutMs) && timeoutMs > 0`. No worker can start until this is a finite positive session deadline.
3. **The host stdout reader is not bounded/fail-closed.** `readline.createInterface` buffers an unterminated line before `acceptLine` can enforce `maxResponseBytes`; `queuedLines` has no cap; unsolicited valid lines are queued; and malformed unsolicited lines are silently ignored because `settlePendingLine` is a no-op when no request is pending. The contract requires host-side total stdout bytes, line buffer, message count, queue and stderr caps, and exactly one response per request. Register the pending response before writing, reject unsolicited/duplicate output, and bound the raw stdout buffer.
4. **The source-closure pin does not cover the host Worker isolate.** `withPinnedResearchModuleLoads` patches the main thread's `Module._load`; the new Worker has a separate CommonJS loader and independently requires the session-thread file, protocol and launcher. `validateBundle` only validates the policy bundle and does not hash/pin this host-side Worker closure. Do not claim the existing main-thread module pin covers it.
5. **Close/abort does not synchronously confirm the host Worker thread has exited.** The thread publishes its shared-buffer result before closing `parentPort`; `closeSync()` / `abortSync()` return after the result without observing the Worker `exit` event. Ensure no session thread leaks across games.

The worker thread may be a useful host-side transport experiment, but it must not bypass the required async fixture architecture or host-side bounded protocol. Please either retire this sync path or explicitly label it experimental and implement the contract-compliant async path separately before wiring it into V3. No fixture or workflow was dispatched by this review.
