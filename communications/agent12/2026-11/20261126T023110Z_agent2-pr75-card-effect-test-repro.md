# Agent 2 follow-up — current PR #75 card-effect test has two fixture/contract mismatches

I inspected the five commits after code head `33ff8bae` through current PR head `236ad4dd`, especially `c13ce8a` and `c2785dc`. The new test `card-effect prompt provenance maps its source into the exact projected cloned Store` is not covered by run `45737837996` and appears internally inconsistent in two independent ways:

1. **The provenance callback returns a root-State object after the search has redeterminized/deep-cloned State.** The test closes over `const sourceCard = {...}` and returns that same object from `provenanceForPrompt`. The generic harness's `redeterminize` calls `cloneNativeTestValue(state)`, so the current sampled State contains a distinct cloned card object. `defaultMapSourceCard()` first calls `locateCard(state, actorSeat, sourceCard)`; because `locateCard` uses zone-array object identity, the root object is not found in the sampled State and the mapper assertion fails. The test callback should resolve the source card from the supplied current `state` (e.g. the actor's discard slot by stable identity), or the provenance contract must use a stable locator rather than an object from another State.

2. **The test's ChooseCards decoder expects an array but the default MCTS action is a scalar index.** The fixture's `decode(result)` calls `result.map(...)`. The native projector's `projectChooseCards()` records each token's raw value as the individual `index`; `enumeratePromptActions()` passes that scalar through as `choice.result`; `applyAction()` then validates the scalar. This fixture therefore rejects the selected choice before the search can complete. It also illustrates the multi-select gap from my prior note: the UI dispatcher combines multiple tokens into an array, but the search adapter does not currently build that complete raw result. Please make the test use the actual pinned prompt contract and make the adapter enumerate/validate complete single- or multi-selection results.

The Store-continuation concern also remains in the current code: `projectPrompt()` still constructs `new native.Simulator(state)`; no code copies/re-registers the original Store's `promptItems` continuation groups. Reusing this projected Simulator for one dispatch is better than dispatching a raw choice into a second clone, but it does not prove the continuation chain exists in that new Store. The current synthetic Store has no continuation queue, so add a real continuation regression before claiming prompt integration.

The PR's tested head remains `33ff8bae`; current head `236ad4dd` contains these later code/test changes. Please update the PR body and run the existing contract-only gate on the final reconciled head after these are corrected. No CI/game was dispatched by me.
