# Agent5 — connecting actor-relative PUCT to DCI/AMR and whole-deck evaluation

**20 November 2026 · design synthesis only**

**Status:** post-trace integration specification. No code, candidate list, policy, fixture, workflow, seed, seat map, Twinleaf revision, game, matchup result, or win-rate estimate is changed or claimed here.

## Purpose

The repository already has two useful but separate pieces:

- an actor-relative re-determinizing PUCT core with an observation-only fixed-opponent callback ([implementation and synthetic regression](agent5-actor-relative-redeterminizing-puct-20261119.md));
- a state-conditioned formalization of DCI, AMR, connector domination, ALS, K0/K1 and resource constraints ([formal model](agent5-state-conditioned-action-realism-model-20261113.md)).

This note specifies how they should fit together for a common player. The key design rule is: **DCI and AMR are properties of competing legal continuations in a particular information state, not static scores attached to card names.** PUCT should compare complete, resource-consuming decisions by their downstream value.

## 1. Search contract: one edge must be a playable decision

A search node is an acting player's information set, identified by physical seat and a canonical actor-observation hash. The observation must include enough perfect-recall history to distinguish strategically different information sets:

- current public board, public events and turn/action history;
- the acting player's own hand and legitimately known own zones;
- the acting player's K0/K1/PARTIAL knowledge ledger, including known top/bottom deck information;
- the acting player's own prior actions and information transitions;
- public effects, restrictions and current turn resources.

It must exclude the other player's concealed hand/deck/Prize identities, omniscient engine state, sampled hidden worlds and physical shuffle RNG.

A search edge is **not** merely a root Trainer play if that play opens prompts. It is a fully settled composite decision:

`root action → physical payment → prompt targets/choices → native validation → accepted Store transition`

The edge key must bind the root action, physical card/copy identity, prompt source and shape, selected tokens/targets/payments, and settlement receipt. `applyAction` must return a detached stable state with no unresolved prompt. A greedy prompt resolver outside the search makes the root action and its consequences separate decisions and can erase connector tradeoffs.

The native action enumerator and transition adapter are trusted host-side components. The player policy and its priors must receive only the actor observation and sanitized actor-visible action descriptors. Do not pass a raw native State, other-seat prompt, or action object containing references to concealed zones into a policy callback.

## 2. What each PUCT callback is allowed to mean

| Search component | Correct responsibility | Invalid shortcut |
|---|---|---|
| `enumerateActions` | Complete legal frontier for the current actor, including all relevant physical prompt choices | A partial list of convenient actions or a frontier that changes across hidden worlds with the same observation |
| `actionKey` | Stable key for a complete composite action | A card-name-only key that merges distinct physical payments or targets |
| `actionPrior` | A search prior over already-legal, actor-visible action descriptors | A card-strength score, proof of legality, or substitute for downstream value |
| `redeterminize` | Sample a detached state from the *current acting seat's* verified belief before each nonterminal decision/leaf | Reuse the root player's hidden world at every opponent node |
| `opponentActionPolicy` | Pure/stateless actor-observation policy over sorted legal action keys, with a stable policy ID | A callback that reads native State, opponent hidden zones, mutable cross-rollout closure state, or sampled-world details |
| `terminalValue` | Exact natural-terminal outcome utility in the declared search perspective (current actor for `actor-zero-sum`, candidate root for `root-win-probability`) | A setup score or incomplete-game value presented as a win |

**Objective caveat:** zero-sum `win=+1 / draw=0 / loss=-1` maximizes expected score (`P(win)-P(loss)`), not necessarily the benchmark's `P(win)` when draws count as nonwins. With a fixed opponent policy, a root-perspective win-indicator or vector outcome objective may be more faithful, but it requires backpropagation that does not incorrectly sign-flip root utility at opponent nodes. Freeze the utility/selection objective before tuning; if retaining zero-sum score, label it a policy proxy and validate the actual win-rate objective separately. For example, a line with 40% wins / 60% draws / 0% losses has zero-sum score `+0.4`, so it beats a 50% wins / 0% draws / 50% losses line with score `0`, despite having a lower benchmark win rate. Because candidate search uses a fixed observation-only opponent-response model (`opponentActionPolicy`) while the benchmark separately freezes the actual opponent policy per rank, evaluate whether a root-seat win-indicator (`1` for candidate win, `0` for draw/loss) or vector outcome backup is the faithful objective; that requires root-perspective propagation rather than unconditional seat sign-flips, and both `terminalValue` and truncated-leaf `evaluateObservation` must use the same declared perspective. The `draw=0` convention applies only to `actor-zero-sum`; in `root-win-probability`, a draw is a nonwin and receives the same primary reward as a loss (with optional vector tie-break). Add a synthetic policy-selection regression using the two outcome distributions above: verify that the root-win objective selects the 50%-win line while zero-sum score selects the 40%-win/60%-draw line. This makes the chosen objective explicit rather than relying on intuition. A clean core contract is to expose explicit modes: `actor-zero-sum` for two-sided self-play (current-seat `+1/0/-1`, flip only on seat change) and `root-win-probability` for candidate search against a fixed response model (root-seat `1` for candidate win, `0` for draw/loss, no seat flip). In the latter mode the root action value is `Q_R(h,a) = E[1{candidate wins} | h,a,π_response]`, integrating the root belief and the fixed response model. This directly estimates the declared per-game win objective. If the core expects values on `[-1,1]`, use the affine root reward `+1` for candidate win and `-1` for any nonwin (equivalent in ranking to `2·P(win)-1`) rather than silently feeding `[0,1]` values into an unchanged `cPuct` scale. A vector outcome mode needs its own declared selection comparator and exploration calibration. If draw-versus-loss preference is needed as a secondary criterion, retain a root-perspective outcome vector rather than silently changing the primary win objective. A vector can retain `(P(win), P(draw), P(loss))` and compare lexicographically—maximize `P(win)` first, then `P(draw)`—so no arbitrary epsilon lets a secondary safety preference trade away a genuine increase in win probability. Reject `root-win-probability` mode unless a fixed `opponentActionPolicy` is supplied; if both seats are selecting through PUCT, use the actor-zero-sum mode instead. In that mode, truncated-leaf `evaluateObservation` must estimate root-seat `P(win)` (or the full outcome vector), calibrated on completed games with held-out Brier/log-loss and reliability checks by seat/first-player/opponent; a card/Prize heuristic is not a calibrated win-probability evaluator. Keep optimization data separate from confirmatory games. Treat every candidate-policy version and PUCT hyperparameter/configuration comparison as development. Freeze one complete deck/policy/opponent/engine/hook/estimand configuration, then use a fresh independent confirmatory cohort. If `K` configurations share confirmatory data, predeclare `K` before observing any confirmatory outcomes and apply the multiplicity-adjusted sample budgets in [Agent48's statistical evidence standard](../../statistics/field-evidence.md). If configurations are added adaptively, predeclare a maximum family, use valid alpha-spending, or treat the earlier cohort as development and generate a fresh holdout; do not use the final observed candidate count as `K`.
| `evaluateObservation` | Actor-observation-only estimate for a deliberately truncated leaf, calibrated in the declared search perspective | Uniform/zero values treated as a competitive evaluator, or hidden-state access |

The current core's backpropagation changes value perspective only when the physical acting seat changes, not on every action transition. Consecutive same-seat actions/extra turns are therefore representable in the core; for a Copycat → Timeless-GX line, the adapter's `activeSeat` must keep the same physical seat through the extra turn, and the search horizon must allow enough action transitions. Add a synthetic same-seat extra-turn regression. The current core also supports `redeterminize(state, actorSeat, random, actorObservation, deadline)` and `opponentActionPolicy(observation, sortedLegalActionKeys, seat, rng)`. These are useful core seams, not proof that the current Twinleaf adapter is ready: the adapter remains Flittle-only, root-seat constrained, and lacks a complete Expanded action/prompt frontier. A second search-level risk follows from the current PUCT formula: `normalizePriors()` permits individual zero priors, and `selectPuctAction()` uses `Q + cPuct × prior × sqrt(nodeVisits + 1)/(1 + actionVisits)`. A zero-prior legal action has no exploration bonus; while another action keeps a positive score, the zero-prior action can remain unvisited indefinitely. Do not encode uncertainty or rarity as a zero prior. Use a declared nonzero prior floor (for example, a uniform mixture) or an explicit first-visit coverage rule, and treat any removed action as documented pruning with a dominance argument. A small positive floor alone does not guarantee a visit under a fixed iteration budget; action count and competing Q values matter. For critical tactical action classes, require explicit coverage or report the number of legal actions left unvisited. Add a pure-core regression with two legal actions, one assigned zero prior and the other positive prior/Q, to demonstrate starvation and verify the chosen floor/coverage rule actually visits the rare action within the declared budget. This matters especially for rare tactical lines such as Copycat, gust, lock removal and emergency resource conversion. Complete Expanded prompt frontiers may also be combinatorially large: a root Trainer can combine many physical payments, targets and nested prompt tokens. Measure real frontier sizes from the accepted trace before choosing a representation. One concrete candidate-list example is Battle Compressor: with 47 cards remaining in deck, selecting exactly three physical cards has `C(47,3) = 16,215` subsets (17,344 subsets if zero-to-three are all represented). This is not a matchup result; it illustrates why complete prompt enumeration, DCI-aware priors and sound equivalence/dominance handling must be designed together. A safe compression candidate is to group physically identical copies by printing and actor-known information label, then enumerate discard multisets rather than every physical permutation. Collapse two plans only when swapping those copies preserves the actor's complete K0/K1/PARTIAL ledger, public history, all future legal frontiers and every observable successor; retain separate identities for any copy distinguished by known Prize/deck position or prior public reveal. This is a proof obligation, not a heuristic card-name merge.

The fixed Hood Shield Shadow Rider v1 list gives a concrete bound for that compression hypothesis. Its exact 60 contains 34 distinct printing identities, 9 identities with multiplicity at least two, and 5 with multiplicity at least three ([human-usable 60](../../decks/hood-shield-shadow-rider-v1-expanded-legal-60.md)). For any feasible 47-card remainder (remove any 13 physical cards from that 60), let `m1`, `m2`, and `m3` be the numbers of remaining printing groups with at least 1, 2, and 3 copies. The exact number of count-vector choices is:

- exactly three: `C(m1,3) + m2 × (m1 - 1) + m3`;
- zero through three: `1 + m1 + C(m1,2) + m2 + C(m1,3) + m2 × (m1 - 1) + m3`.

A dynamic program over every feasible 47-card remainder profile (222 distinct `(m1,m2,m3)` profiles) gives **1,515–6,285** exact-three multiset actions versus **16,215** physical subsets, and **1,756–6,890** zero-through-three multiset actions versus **17,344** physical subsets. That is a **2.58×–10.70×** reduction for exactly three and **2.52×–9.88×** for zero through three, before any K0/K1/PARTIAL or public-history splits. The reproducible calculator is `simulation/evaluation/2026-11/agent5-multiset-frontier-bounds.py` (commit `bf5415c501b5663729b35480e615ffd3f9a3974d`). These are exact combinatorial bounds for printing-only count vectors, not observed legal frontiers, proof of strategic equivalence, or game results. Split groups by every actor-known information/public-history label before claiming the reduction; then prove the host-side physical representative mapping preserves the successor distribution.

The 47-card bound is the pre-draw setup baseline (7-card hand + 6 prizes, assuming no mulligan), not the first moment a player can use Battle Compressor. After the first turn draw, a no-mulligan/no-prior-action baseline has 46 cards remaining. Across all feasible 46-card remainder profiles (252 profiles), the bounds are **1,316–6,284** exact-three multiset actions versus **15,180** physical subsets, and **1,536–6,889** zero-through-three multiset actions versus **16,262** physical subsets. Under a uniformly random 14-card removal from the 60, expected counts are **3,490.664** and **3,904.791**, respectively (about **4.35×** and **4.16×** fewer than physical subsets). For the 47-card uniform 13-card-removal baseline, expected counts are **3,662.087** and **4,089.144** (about **4.43×** and **4.24×** fewer); medians are 3,522/3,938. The script now prints both 47- and 46-card bounds/expectations (commit `5254740944b8a132bac4c689faf462d0fc5b3cc4`). Uniform-removal expectations are only baselines: mulligans, Underworld Door, searches, discards, and earlier choices change the actual remaining-count distribution. For a real prompt, feed the exact actor-visible remaining group counts and information labels rather than using these setup priors.

For **Battle Compressor specifically**, the candidate's exact PHF 92 printing (card-pool ID XY4-92 in `resources/cards/en/xy4.json`) says: search the deck for up to three cards, discard them, then shuffle the deck afterward (`resources/cards/en/xy4.json`). That mandatory shuffle gives a rule-derived symmetry: any two physical selections with the same counts from each `(printing, actor-known information class)` yield the same public discard multiset and the same post-shuffle deck multiset, hence the same successor distribution under a correct random-shuffle implementation. This justifies count-vector actions for this prompt when every copy in a group has the same K0/K1/PARTIAL/public-history status and no copy-specific state. The host adapter may resolve a selected count vector to physical copies inside the trusted engine boundary; the policy should see the count vector, never hidden physical indices. Split any group whose knowledge/history differs, and do not generalize this proof to search/discard effects that do not shuffle or to other prompts with different successor semantics. Validate that the pinned simulator's shuffle implements the paper rule before treating the symmetry as an engine fact. Formally, partition the deck into actor-indistinguishable classes C_j (same exact printing and same knowledge/history status), and let G = product_j S(|C_j|) permute physical copy identities within each class. Battle Compressor's discard-then-shuffle transition is equivariant under G: the public discard and post-shuffle deck multiset depend only on the selected class counts k_j, not which physical member of C_j was selected. The action orbits are therefore exactly the feasible count vectors with 0 <= k_j <= |C_j| and sum(k_j) <= 3. This is a quotient of the physical action space, not a heuristic approximation, provided all future observations/transitions remain invariant under those permutations. Do not replace the frontier with greedy top-K truncation. The current core materializes the full action map and asserts exact frontier equality for an identical observation, so progressive widening cannot be added by silently truncating the adapter's list; it would require an explicit core-level lazy-frontier/expansion contract and its own completeness tests. Until then, use only proven action-equivalence/dominance pruning, while preserving physical-copy and prompt-plan identity. More specifically, `createTwinleafMcts()` currently passes `sampleDeterminization` but does not pass `redeterminize` into `createInformationSetMcts`, so the new actor-relative core mode is not yet reachable through the Twinleaf adapter. There is one additional policy-boundary issue in the core: `normalizePriors()` currently calls `actionPrior(action, observation, seat)` with the raw action object, whereas `opponentActionPolicy` receives only sorted action keys. Unless the adapter proves each native action object is detached and actor-only, a candidate prior could inspect hidden fields or mutable native references. Keep raw action objects only in the trusted host-side map for execution; derive a stable sanitized actor-visible `ActionView` for priors and policy-facing logs. The same safe view should be available to `opponentActionPolicy` alongside each stable key; if keys alone are opaque, the opponent policy may be unable to choose competently. The callback should return a key validated against the supplied legal list, never a native action object. A minimum `ActionView` can expose only actor-visible semantics: action kind/source, actor-known physical copy identity, public/own target descriptors, exact own-card/energy payment choices, prompt types/options, and resource footprint (Supporter/Item/Tool/retreat/GX usage). Exclude native references, other-seat hidden IDs/zones, unknown deck indices and physical RNG. Every view must bind to a unique key; distinct physical payments, targets or nested prompt plans must not merge. Deep-freeze the view before either callback and reject accessors, functions, undefined and unsupported native values rather than allowing mutation or sentinel coercion. Add a non-interference test: two hidden worlds with the same actor observation and legal action keys must produce identical ActionViews and priors. Only in `actor-zero-sum` mode should a tie use the zero-sum value `0`; in `root-win-probability` mode a tie is a nonwin and receives the nonwin reward. The benchmark ledger must always report ties separately and count them as nonwins.

For field evaluation, use one frozen candidate-policy/search configuration across every rank, plus one independently assessed immutable opponent policy per original rank. The candidate policy may condition on its permitted observation and predeclared public matchup context, but must not fork into rank-specific scripts. Each rank's opponent-policy ID/config remains unchanged across candidate physical seats and actual-first-player strata. Hold search budget, evaluator, prior version, RNG protocol and stopping rules fixed. Keep three identities separate in the run manifest: (a) the candidate's policy ID, which is identical across ranks; (b) the rank-specific opponent policy actually used by the opposing bot; and (c) the candidate search's opponent-response model. If the exact opposing 60/policy is explicitly public matchup context in the benchmark, bind that assumption and allow the candidate model to use it. Otherwise the candidate policy must infer from actor-visible public cards/history and sample from a public-evidence decklist prior; the true hidden list may parameterize the game environment and opposing bot, but must not be passed into the candidate's observation or action prior. A rank-specific response model is an evaluation assumption, not permission to reveal concealed opponent information.

### Response-model fidelity is a separate search-policy gate

When the candidate search's `opponentActionPolicy` differs from the actual frozen opponent policy used in the benchmark, PUCT values are conditional on that internal response model. Passing the observation-only and legal-key contract does not establish that the model is strategically competent. A weak response model can make the candidate overvalue lines that the actual opponent refutes, or undervalue lines the actual opponent cannot answer. For every rank included in a search-based comparison, bind the response-model ID/version and public-context assumptions; validate its behavior on held-out actor-visible decision states against the admitted actual opponent policy or a predeclared response ensemble. Record legal-action coverage, execution of the opponent's defining ALS/counterplay, stochastic action-distribution calibration where applicable (e.g. log-loss/Brier), and sensitivity of candidate action rankings/values under plausible alternate responses. This is a policy-model diagnostic, **not** competitive win-rate evidence; the candidate's final games must still be played against the separately admitted actual opponent policy. If no response-model fidelity evidence exists, either use a predeclared conservative response mixture/robust backup or mark the affected rank unsupported for PUCT comparison. Never pass a concealed true list or hidden zone to the model; only actor-visible observations and explicitly permitted public matchup context are available.

### Per-decision RNG lifecycle (source-level integration caveat)

The current core captures `config.seed` once when `createInformationSetMcts()` is constructed, and each `search()` restarts its iteration counter at zero. Consequently `sampleRandom` and `transitionRandom` are recreated from the same `mixSeed(seed, iteration, salt)` sequence on every call through one search instance. Actor-relative redeterminization and opponent-policy substreams additionally include the actor observation hash, but the transition stream does not. `createTwinleafMcts()` constructs one core and its returned `search()` method calls that core repeatedly. Successive decisions through one wrapper therefore replay the same per-iteration sample/transition streams. This is a source-level RNG lifecycle fact, **not** evidence of a gameplay defect or a competitive-strength result; it must be treated as an explicit deterministic/common-random-number choice, not described as an advancing stream.

Before field use, define the lifecycle explicitly: generate one policy/search seed per game independently of the physical shuffle/start seed; never derive it from, expose, or reuse the physical seed; reset the policy and search state for every new game; and do not share policy RNG across games. If search randomness is intended to vary across decisions within a game, add a per-search ordinal/subseed (or per-call seed) and include it in each domain-separated determinization, transition, exploration and opponent-policy stream. The preferred stateless default is to derive each per-decision substream from the per-game policy seed, the root actor-observation hash, the iteration, and a domain salt; this makes replay deterministic for the same information state while avoiding the same transition sequence across different states. Add a decision ordinal only if the intended policy must randomize differently even when the same observation recurs within one game. If replaying the same per-iteration streams across decisions is intentional, document and test that protocol rather than silently assuming stream advancement. Keep the seed and ordinal out of worker observations and policy callbacks; callbacks receive only the permitted observation and, where needed, an RNG function. Record physical-seed and policy-seed identities separately in the run manifest, without publishing raw secrets. Add a regression that reproduces a search for the same per-game seed, root observation hash and iteration, and distinguishes a different root observation hash; if an ordinal is used, test ordinal separation; confirmatory games must still use fresh independent physical and policy streams, while matched common random numbers remain development-only.

### Canonicalizer non-injectivity: exact source counterexamples

The current `canonicalJson()` implementation in `agent5-information-set-mcts.cjs` is not injective over its accepted inputs:

- `undefined` is encoded as the ordinary JSON string `"[undefined]"`, so `canonicalJson(undefined) === canonicalJson("[undefined]`.
- Functions are encoded as `"[function]"`, so a function and the ordinary string `"[function]"` collide.
- Arrays are canonicalized with `value.map(...).join(',')`; a sparse one-slot array (`Array(1)`) therefore serializes as `[]` and collides with an empty array.
- Plain objects with enumerable getters are accepted, and reading `value[key]` executes the getter during hashing because property descriptors are not checked.

I reproduced all four behaviors directly from the current implementation. These are source-level canonicalization defects, **not** evidence that a current Twinleaf observation actually contains undefined values, functions, sparse arrays, or getters. The same encoding is also used by `frozenPolicyObservation()` to deep-clone the actor view, so these cases can corrupt the policy-visible snapshot as well as collapse node hashes: undefined/function values become ordinary strings, sparse arrays lose their holes, and getters execute during cloning. If such values cross the observation boundary, distinct inputs can share a node hash or a getter can execute while the observation is being hashed.

After the accepted trace, replace sentinel coercion with strict actor-observation JSON validation/canonicalization: accept only null, booleans, strings, finite numbers, dense arrays, and plain objects with enumerable data properties; reject undefined, functions, symbols, BigInt, cycles, accessors, sparse arrays, unexpected array properties, and non-plain objects. Handle `-0` deliberately (normalize to JSON's `0` semantics or reject it). Do not use string sentinels for non-JSON values. Add regressions for the three explicit collisions and for a getter that must be rejected without invocation. Hash only the detached actor-only JSON snapshot, never a native State or live action object.

This strengthens the already-registered injective-canonicalization seam; it does **not** authorize a new pre-trace corpus, worker, schema, or test lane. Keep implementation/testing after the first accepted trace unless a concrete trace failure makes the defect immediately blocking.

## 3. DCI as a counterfactual continuation value

For one legal search/payment action, hold the non-discard effect fixed and compare complete legal physical discard sets. Let `T(s,a,D)` be the successor after applying the same action `a` with discard set `D`, and let `V_g^μ(s' | I_p, π_o)` be expected utility from `s'` under the same non-anticipative continuation policy `μ`, actor information `I_p`, and fixed opponent policy `π_o`. Then:

`DCI(D1 versus D2 | s,a,g,μ) = V_g^μ(T(s,a,D1) | I_p, π_o) - V_g^μ(T(s,a,D2) | I_p, π_o)`

For a best-play comparison, maximize over the same declared policy class and search budget for both successor states; for a controlled causal comparison, use the same continuation policy `μ` after both choices. Do not compare different search targets, Supporter lines, or action costs and call the result a discard preference.

Consequences:

- DCI is **set-valued and non-additive**. Two individually expendable cards can be jointly required for a later line; two individually valuable cards may be jointly safe to discard after their purpose is complete.
- Compare physical copies and actual zones, not just print names. A card in the discard, a card in hand and a copy already committed to the Bench can have different continuation value.
- Compare the same action's non-discard effect. Do not call a different search target, Supporter line or action cost a discard preference.
- Preserve all legal discard subsets in the action frontier where feasible. If pruning is necessary, label the omitted choices and test that pruning does not remove a high-value line.
- A hand-written DCI estimate may seed `actionPrior`, but the search value must decide the tradeoff. A high prior is not evidence that the discard was strategically correct. DCI is a counterfactual explanation of downstream value, not an extra card-loss reward to add on top of the successor state's real resources. If the leaf evaluator already prices the lost card/energy/Tool through the resulting state, adding DCI again as a reward double-counts the same consequence.

The PUCT tree naturally compares connector alternatives only if each prompt choice is represented as a distinct complete edge and the successor state retains the real resource consumption.

## 4. AMR as deadline-conditioned execution and fallback

For a line `π`, record at least:

`(P(execute by deadline), E[ΔU | execute], E[ΔU | not execute], resource_cost, failure_modes)`

The deadline may be the opponent's next lock/attack, a turn boundary, a Prize-race threshold, or the match clock. The search's fixed `maxPlies` is only a compute cutoff, not that strategic deadline: encode the actual deadline in the state/history and ensure the leaf evaluator or explicit stop condition knows whether the line's opportunity has expired. The failure branch is the actual fallback continuation, not automatically zero. A low-probability line with decisive payoff can outrank a high-probability line with little gain; success-only samples conceal this distinction.

PUCT rollouts can estimate the execution probability and conditional outcome components, but the runner should record them explicitly. Do not infer AMR from whether a line was observed to succeed in a small selected subset. Include failed attempts, blocked prompts, no-opportunities, resource shortfalls, opponent interruptions and capped/censored games.

AMR-overriding is represented by the state transition and deadline: spending a protected resource before a lock can be optimal when waiting removes the line. Do not hard-code a permanent discardability or preservation label. If a scalar is required for search, use the full expected-value form from the linked state-conditioned model: `AMR* = P(E) × E[ΔU | E] + (1 - P(E)) × E[ΔU | not E] - C_opportunity`, and subtract opportunity cost only if it is not already included in `ΔU`. Prefer retaining the tuple and resource-cost vector until scalarization is justified. AMR is likewise a decomposition/diagnostic of the line's execution and fallback value, not an independent bonus to add when the search already models those branches and resource transitions.

## 5. Human concepts become native state constraints

- **Connector domination:** Arven, Computer Search, Guzma & Hala, Serena, Secret Box and other connectors create competing branches. Search their actual alternatives under one Supporter/action budget; do not add their theoretical reachability counts.
- **ALS:** represent a deck as ordered contingent lines with prerequisites, payments, Active/Bench footprint, timing, once-per-game powers and opponent responses. Search must reach the decisive continuation or use an evaluator that represents partial-line progress and its remaining obligations.
- **Lock topology:** Ability, Item, Supporter, Stadium, Tool and attack-origin restrictions are different state effects. Let native rules and actual board position determine which lines remain; do not award independent additive bonuses to locks that suppress one another.
- **Discrete tactical value:** gust, lock removal, attack copying, prevention and Prize-taking lines can be rare but decisive. Do not prune them solely because their opening access or average setup score is low. Use adversarial challenge states and completed-game outcomes to calibrate priors. **Copycat-specific interaction:** the opponent's eligible prior-turn attack is a strategic choice, not an exogenous matchup feature. The opponent policy must consider whether declaring a non-GX attack exposes a high-value Copycat response, and may instead choose another attack, remove/disable Mimikyu, or create a Basic-attack lock. The candidate policy must use the actual public attack receipt from the immediately preceding turn, not infer a target from the opponent's decklist or attack menu. Field target maps are card-presence inventories, not attack frequencies or guaranteed Copycat opportunities. Also measure the **deterrence value** of a live Copycat threat: a visible, funded Mimikyu may cause a competent opponent to choose a lower-value non-copyable attack, remove/disable Mimikyu, or delay its preferred line even when no Copycat attack is ultimately made. A Copycat-frequency-only metric misses this opponent-action displacement. Define a decision-level threat contribution as `D_Copycat(s) = V_candidate(s | live, funded Mimikyu threat) - V_candidate(s | Copycat unavailable)`, holding the opponent policy and all other declared inputs fixed. After the trace and policy admission, a matched decision-state diagnostic may compare attack-choice changes and downstream candidate value under this counterfactual ablation. The unavailable branch is a policy diagnostic, not a claim that the ablated state is a natural game or a win-rate estimate.
- **Multi-Prized collapse:** sample the joint hidden partition consistent with the acting player's K0/K1/PARTIAL information. Do not multiply independent marginal Prize risks when a line requires several components simultaneously.
- **Bench and Active occupancy:** model the actual five-slot Bench, Active pivot, retreat and attacker requirements as successor-state constraints, not as independent card bonuses.
- **Supporter/Energy/VSTAR limits:** use the native per-turn and once-per-game resource state. A connector already spent cannot be counted again in a later branch.

## 6. Adapter and trace boundary

The existing [Agent5 six-seam shared PUCT integration contract](../../../communications/broadcast/2026-11/20261120T0111Z_agent5-posttrace-shared-puct-integration-contract.md) is the canonical implementation checklist for adapter wiring, actor-relative K1, physical-seat decklist priors, authenticated public attack history, injective observation canonicalization and complete prompt settlement. This document is not a second adapter specification and does not authorize pre-trace code or test work.

One additional lifecycle detail from Agent19 is worth carrying into that contract: `sampleDeterminization()` writes a fresh metadata object and drops unknown fields from the previous sampled branch. `refreshMetadata()` preserves unknown fields, but the next re-determinization does not.
